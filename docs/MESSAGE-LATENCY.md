# 消息延迟与 0.6.4 优化

BiliCinema 的已连接客户端通过 WebSocket 直接发送聊天帧，云端房间立即广播。Whisper 则先在客户端加密，通过 HTTPS 提交、写入 D1，提交后通知在线设备，再由接收端补拉密文并解密。两者消息持久化和确认语义不同；不能把差异都归因于加密。

0.6.4 保留现有加密和持久化，缩短以下步骤：

- CLI：服务器声明 `send-key-check-v1`、当前会话已同步且身份检查通过时，省去每条消息发送前的一次同步。服务器在实际写入语句中校验 `recipientPublicKey` 与当前接收方公钥；身份冲突返回 409 且不写入消息、图片或 journal。冲突后只同步核对，不自动重发。旧服务器或未同步会话保持原流程。
- 网页 / App：提交回执返回已保存的消息元数据与密文，当前会话立即呈现已提交消息，通常无需再为自己的显示额外拉取。晚到回执不能覆盖已同步的删除或图片消费。同步游标仍只随增量同步推进，不能因回执跳过其他变化。
- Worker：消息通知使用的 journal 起点读取并入写入批次，省去一次独立的串行 D1 往返。SQL 语句及必要 journal 写入仍存在，不能说成数据库读写减半。通知继续放在提交之后异步执行，通知失败不改变提交结果。

手动复现本机合成检查：`node scripts/measure-send-latency.mjs`。脚本使用临时密钥、合成短文本及模拟网络延迟，只输出聚合计数和耗时，不连接正式站、不输出聊天正文、密文或凭据。密码派生不计入在线消息的加解密时间。

本次 Windows 本机的 200 条短文本：加密中位数约 0.140 ms、P95 0.217 ms；解密中位数约 0.094 ms、P95 0.117 ms。5 条顺序排队发送在每次模拟往返设为 20 ms 的模型中，发送前同步与 POST 合计请求从 10 次变为 5 次，耗时约 305 ms 变为 156 ms。Windows 定时器调度会使实际模型等待超过设定值；此模型不包含之后的接收端同步、应用渲染及互联网链路。

这些数据不代表正式 Cloudflare 延迟、P95、用户所在地网络、Android 真机性能或用户容量。正式网络的 TLS 建连、线路抖动、Cloudflare 边缘至 D1 的往返仍可能占主导。没有对正式站压测，没有用真实聊天或凭据采集性能。
